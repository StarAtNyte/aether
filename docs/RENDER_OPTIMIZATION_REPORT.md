# Renderer optimization report

Date: 2026-11-05. Scope: source review, targeted changes, and bounded tests on this machine. Results and their limitations are documented below; a sustained 60 FPS at full quality is not yet established.

## Changes

1. **Still path tracing:** an attempt to skip intermediate presentation during sample accumulation was reverted after a tiny-scene comparison produced different output pixels. The final renderer uses its original presentation path; see the follow-up below.
2. **Capture target retention:** `packages/render/src/gpu/capture-targets.ts` adds an LRU with a 32 MiB estimated color-plus-depth budget and a two-target count limit. Targets with pending asynchronous readbacks are retained until all reads complete; the budget can be exceeded temporarily. An oversized target can remain during a capture and is released after its last read or capture completion. This estimate assumes 8 bytes per pixel and excludes driver overhead; it is a policy estimate, not a GPU memory measurement. Reallocation may add latency to a later large capture. Capture pixels and resolution are unchanged.

Validation: `npm run typecheck` passed. `npx vitest run packages/render/test/capture-targets.test.ts packages/render/test/pathtrace.test.ts packages/render/test/pathtrace-filters.test.ts --maxWorkers=1` passed (18 tests). These are not GPU image or performance tests. One initial cache test had an incorrect expectation about which unpinned target is evicted under pressure; it was corrected and the targeted suite passed.

## Bounded hardware runs, 2026-11-05

The user requested real-device testing without risking the rest of the machine. We used the existing `default-perf.e2e.ts` harness, Intel UHD WebGL2, Chromium headless, 1280×800 CSS pixels, one world at a time under `heavy2.lock`, a systemd cgroup with no swap and `CPUQuota=200%`, nice 15, and a 180–210 second timeout. The cap covers the benchmark browser, test and server process group, not the whole desktop. The current build included the still-trace and capture-cache changes above. Logs are in [benchmark/renderer-2026-11-05](benchmark/renderer-2026-11-05/).

- **Lisbon Hills**, cap 4,600 MiB: the default scene loaded at 148.9 s with 1,831 draws, 7.01 M drawn triangles, 213 textures (357.2 MB reported), and a 1216×736 drawing buffer. During the requested switch to the `ultra-adaptive` row, the process group reached the cap (systemd `MemoryPeak=4823449600`, result `oom-kill`) and the browser closed. No orbit frame-time result was obtained. This is not proof of which allocation caused the peak. The cap was not raised.
- **Kestrel Outpost**, cap 4,000 MiB: default row finished before and after the shared-buffer change below. The harness reports best-block median/p90 of 6.5/7.2 ms before and 4.6/4.8 ms after; its separate reported CPU values were 12.7 and 20.7 ms. Systemd rounded peaks to 2.2 and 2.1 GiB. These are single profiled, uncapped-frame-rate runs, with differing draw and GPU samples, not a statistically reliable improvement or an input-latency measurement. The built-in profile aggregated 2,125 ms and 3,159 ms respectively in `bufferSubData` over the measurement window; that aggregate includes other uploads and does not identify the changed buffers. The `--vsync` flag in these two runs was silently ignored by the harness because it only parsed `--vsync=value`; this parser was fixed after the runs started. Do not compare their timings directly to the earlier vsynced measurements.
- **Cliff Sanctuary**, cap 4,600 MiB: post-change default row completed in 75.5 s, with systemd reporting a 3.3 GiB peak. The harness reported best-block median/p90 30.1/33.4 ms; individual orbit blocks reported rAF medians 33.3/49.9/33.3 ms. It ran at automatic low tier and reported motion resolution scale 0.5; those existing adaptive settings affect image quality and make this unsuitable as evidence of full-resolution or ultra performance. This run used `--vsync=1` and no CPU profiler. No pre-change counterpart was run, so it does not measure the optimization's effect.

**Shared engine change evaluated:** `StaticBatches` was temporarily changed to static buffer usage for the Kestrel comparison. A later same-frame capture test found this unsafe and the change was reverted; the Kestrel after-run therefore does not measure the current code. Surroundings trees retain static usage because their matrices are set only on creation. In the installed three.js common renderer, `DynamicDrawUsage` causes an upload on every attribute use even without a version change.

**Verification:** the production build passed under a 2,300 MiB memory cap; the five focused batch, surroundings, capture-cache, and path-trace suites passed (42 tests). The final type check exceeded an initial 1,800 MiB cap and passed when retried alone under a 3,000 MiB cap. `git diff --check` passed.

## Follow-up: particle uploads and capture correctness

The six particle attributes now use the default static usage. Particle writes already increment attribute versions and retain dirty ranges until consumed, including while hidden. This avoids three.js's unconditional dynamic-buffer uploads on additional render passes while leaving simulation, particle counts, and shading unchanged. Weather and static batches retain dynamic matrix usage for capture correctness, as explained below.

The bounded `tests/e2e/instance-upload.e2e.ts` check renders small scenes using the installed common renderer. On Intel WebGL2 and software WebGPU, unchanged direct particle attributes produced zero static-buffer updates versus three dynamic-buffer updates over three draws. A particle-attribute update between two draws produced one upload, and the static and dynamic images matched byte for byte. A separate 2,048-instance matrix test found a crucial exception: moving an instance between draws in the same node frame produced different pixels with static usage. The matrix variant copies through a three.js interleaved buffer synchronized by a node-frame callback; capture and weather can update those matrices more than once in a frame. The earlier static-batch change and a proposed weather change were therefore reverted. The simple test does not establish full-scene image parity, a heavy-world FPS gain, or sustained 60 FPS. Both browser runs used 1,800 MiB and 150% CPU caps and a 45 s timeout. See [the test log](benchmark/renderer-2026-11-05/instance-upload-check.txt).

After the reverts, the VFX, weather, static-batch, and surroundings suites passed (46 tests); typecheck passed under a 3,000 MiB cap.

## Follow-up: bounded dynamic-matrix upload experiment

An experimental cache kept dynamic instance matrices, compared their exact CPU bytes before each full upload, and fell back to three.js for partial updates. A 2 MiB cumulative snapshot budget bounded the extra memory. Small controlled Intel WebGL2 and software WebGPU tests verified byte-identical pixels, including a matrix changed between draws in one node frame; three repeated draws caused one actual upload with the experiment versus three without it.

On Cliff Sanctuary with identical `realtime-low` settings, adaptive scaling off, a 1280×800 viewport and 40-frame blocks, the existing harness reported a 50.2 ms best-block median / 66.6 ms p90 without the cache and 52.6 / 66.7 ms with it. Reported renderer CPU values were 34.5 and 34.0 ms; the GPU samples were approximately 43–45 and 46–47 ms. These are single sequential runs, not a statistically conclusive regression or an isolated GPU measurement. The fixed motion scale was 1, but the selected tier was low, so this is not an ultra-quality measurement. Both process groups were limited to 4,600 MiB, no swap, 200% CPU, and 210 seconds; both completed. Raw logs: [cache off](benchmark/renderer-2026-11-05/cliff-instance-cache-off.txt), [cache on](benchmark/renderer-2026-11-05/cliff-instance-cache-on.txt).

Because the heavy-world comparison showed no measured improvement and the cache added CPU comparison work and up to 2 MiB of memory, the experimental production cache and its switch were removed. It did not establish the 16.7 ms needed for 60 FPS. The baseline used `AETHER_NO_INSTANCE_UPLOAD_CACHE=1` to disable the experiment in that temporary build; that switch was also removed and is not needed in the current renderer.

## Follow-up: still path-trace comparison

A temporary small-scene test compared the real offscreen tracer with intermediate presentation enabled and disabled, forcing `stableNoise` and resetting a seeded `Math.random` before each trace. On Intel WebGL2 at 128×72, three samples and two bounces, the images differed in 1,424 RGBA channel values, with a maximum channel difference of 106; the old path invoked the presentation callback five times and the deferred path once. The test did not establish whether all stochastic state was identical between fresh contexts, so it does not prove that skipping presentation caused the difference. It does mean image equivalence was not demonstrated, and the earlier change was reverted to respect the quality constraint. Both attempts used a 2,400 MiB cap, no swap, 150% CPU, and a 90-second timeout. See [the test log](benchmark/renderer-2026-11-05/pathtrace-equivalence.txt).

## Findings and follow-up

- **Batch CPU work:** `sync/draw-batches.ts` validates members and their parent chains per update; `sync/static-batches.ts` scans instance matrices. Dirty versions or change notifications could reduce this work, provided every hierarchy, material, geometry, visibility, layer, shadow, and transform mutation is accounted for. Profile first; an incomplete invalidation scheme can produce wrong images.
- **Water passes:** the backdrop and planar reflection each render the scene. Reuse only when every relevant camera, scene, light, shadow, animation, visibility, target-size and water-plane input remains unchanged. Verify captures and temporal effects. The gain is scene dependent.
- **Memory reporting:** `estimatedGpuMB` is an estimate of framebuffer and shadow allocations, not total GPU memory. Texture bytes are separate. Audit geometry, cached targets, inactive post chains, and transient allocations before using the number to make budget decisions.
- **GPU timing:** the current frame-cost probe measures WebGL timer queries, not WebGPU. Optional asynchronous WebGPU timestamp queries can distinguish scene, water, and post costs when supported. They have overhead and browser-dependent resolution. Instrumentation should not block the frame loop or change normal presentation behavior.
- **Path-tracing startup:** the still tracer synchronously builds a BVH in `setScene`. The installed path tracer supports `setBVHWorker` and `setSceneAsync`; a single `GenerateMeshBVHWorker` is a candidate to improve responsiveness without changing the scene or sampling. Scene preparation and GPU upload may still block; worker startup, transferred buffers, cancellation, CSP, cleanup, and fallback require tests. Avoid parallel workers by default because of CPU and memory pressure. See [three-mesh-bvh worker documentation](https://github.com/gkjohnson/three-mesh-bvh#asynchronous-generation).
- **WebGPU path tracer:** the installed path-tracer package contains a WebGPU implementation; [its upstream repository](https://github.com/gkjohnson/three-gpu-pathtracer) also describes WebGPU compute. Treat migration as an experiment, not a guaranteed speedup or equivalent renderer: compare supported materials, texture handling, lighting, images, memory, browsers, and device-loss behavior with the current WebGL2 still path.
- **Recent ray-tracing research:** [ReSTIR PT Enhanced (2026)](https://research.nvidia.com/labs/rtr/publication/lin2026restirptenhanced/) and [multi-layer reservoir splatting (2026)](https://research.nvidia.com/labs/rtr/publication/hong2026multilayer/) explore spatiotemporal sample reuse. [ReSTIR BDPT (2025)](https://research.nvidia.com/labs/rtr/publication/hedstrom2025restir/) targets difficult transport including caustics. These require a new rendering architecture and additional history and buffers; temporal artifacts, bias, denoising, browser support, and memory must be measured. They cannot be described as guaranteed lossless or dropped into the existing raster pipeline. [MuTracer](https://github.com/pissang/mutracer) is a separate WebGPU-first browser path tracer worth comparing in a controlled prototype, not a drop-in replacement.

## Suggested controlled evaluation

Use fixed scenes and camera paths on WebGPU and WebGL2, integrated and discrete GPUs, and record warm and cold runs. Capture p50/p95/p99 frame time, CPU and GPU pass timings, input-to-next-frame latency, peak and retained memory, and pixel or perceptual differences. Include large static batches, moving objects, water, indoor scenes, large captures, and repeated world changes. Run heavy tests only when convenient for the machine owner.
