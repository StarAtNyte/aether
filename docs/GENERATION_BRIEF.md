# Generation brief

A general prompt ("make a cinema hall") used to come out minimal: the model built the shortest thing that answers the words. The brief makes it plan first, build to that plan, and check the result against it. It applies to a 3D world started from a text prompt (not a photo, not an edit of an existing world): interiors (cinema hall, library, restaurant, church, gym, clinic, school, museum, airport lounge) and outdoor or game worlds (village, harbour, forest camp, sci-fi corridor).

The model looks and judges; code only keeps the books. Counts are advisory evidence. Nothing passes or fails on a number, and no word list in code decides how elaborate a request is.

Source: `packages/agent/src/brief.ts` (schema, instruction text, checklist, evidence), `brief-stage.ts` (the stage), hooks in `agent.ts`. Enabled with `AgentOptions.brief` (the studio sets it for the full prompt profile; the MCP server and the offline planner do not).

## Stages

1. **Brief.** One model call (`submit_brief`), written from the model's own knowledge. It first states `elaboration` with a one-line reason taken from the wording of the request:
   - `elaborate` is the default for a general prompt: a full-scale, detailed result;
   - `minimal` only when the user states a small scale or asks for simplicity ("a tiny cabin", "simple", "just a box");
   - `moderate` in between.
   The model judges this from the meaning of the request; the instruction text carries the rule, code carries no keywords. The richness target follows the statement.
   Then: kind, summary, scale in metres, zones, elements (name, realistic count, size, note, and `find` words for counting), materials, lighting, and a richness target (approximate distinct kinds and pieces, scaled to the world size) with `richness.basis`, the arithmetic behind the counts. A brief that fails validation is sent back once with the reasons; if it still fails the build goes on without a brief, and a step says so.
2. **Reference image (optional, the model's decision).** The brief says whether to look at a generated reference (`reference.generate`) and why: yes for an elaborate request of a specific, visually distinctive space it is unsure about (cathedral, airport, museum, cinema hall); no for simple or minimal requests and for things it knows well. The decision and the reason are recorded either way. When an image generator is connected (the Codex image tool or an OpenAI key, as for `make_texture`; see IMAGE_GENERATION.md) one picture is made. It goes to the model with the checklist, and `look_closer {regions:[{box}]}` (or `{whole:true}`) returns crops of it so the model can pull details. With no generator, or when generation fails, the record says `unavailable` or `failed` and the build uses the brief alone.
   Provenance: `generated reference`, with the prompt, generator and model. The picture is held for the run only; it is never put in the world, the project or the repository. Web search, where a provider offers it, is for ideas in text only: no web image is copied or kept.
   **Counts follow the size.** The instruction text asks the model to work each count out from the floor area, the wall length and the spacing a real place keeps (one painting per 2.5 to 3 m of wall in one row at eye height, a table of four per 5 to 6 m2 of dining floor, a seat per 0.55 m of row, a column per 4 to 6 m of colonnade, 1.2 m aisles) and to write that in `basis`; a 20 x 30 m museum is 20 to 40 paintings, not 150, and too many is as wrong as too few. No number is in code.
   **Stand-ins.** When a wanted element has no matching part or model, the model says so in the element's note and names the nearest sensible substitute or crafts one from primitives; a tree is not a statue. The crafted parts that answer common venue needs (statue, rope-stanchion, plaque, place-setting, candle, column, ceiling-baffle, planter, ...) are named in the text and found by `find_model`.
   **Outdoor worlds.** For a harbour, market, village, forest camp or plaza the instruction asks for the defining elements of the real place, one element each (a harbour: quay edge with bollards and cleats, moored boats of varied size, cranes, warehouses, nets and lobster pots, lamp posts, signage, water with reflections, crates and barrels in small groups, gulls), the edges they follow (quay edge, shoreline, street frontage, trail) and counts worked out from the area and the spacing of the real place (a bollard per 8 to 12 m of quay edge, a boat per 10 to 15 m of berth, a stall per 4 to 6 m of frontage; crates and barrels in clusters of 3 to 8, 20 to 40 on a 60 x 40 m quay). The build puts each element in one instanced call (`shape_land` land, along, row, grid) and asks `find_model` first; crafted parts `furn-boat` (rowboat, dinghy, fishing, sailboat, motorboat, any length, floats with its origin on the waterline), `furn-bollard` (bollard, cleat, mooring pile), `furn-lobster-pot` and `furn-seagull` stand next to the photographed CC0 ships, cranes, buoys, crates and barrels. The checklist asks for under 400 draw calls. The review of a world without a building looks from an overview and from spots well inside its edge at eye height (a person on foot), and asks for what is missing as well as what is over-placed.
   **Exterior.** Any enclosed building gets an element "Exterior facade" (entrance with canopy or surround, lit sign with the name, window rhythm, cornice, plinth, forecourt paving, planters and lamps); the build sets it through `design_plan` `facade` and `exteriorWall`.
3. **Plan shown.** A `brief` event carries the plan. The studio shows it as a collapsible card in the chat. With the setting "Review the plan before building" (Settings, AI connection) the run waits: the user can change counts, drop elements, add a note, and press "Build with this plan". Default: off, the run carries on at once.
4. **Build.** The checklist is part of the first build turn (shell through `design_plan`, repeated elements through the one-call `shape_land` layouts named per element, venue lighting with real lights, a finished exterior): ask `find_model` for each element (crafted venue parts such as the cinema seat, stage, screen, pew, vitrine and library stack come first, then photographed models), place repeated things in one call each with `shape_land` `tier` (raked seating, sightline solved), `grid` or `row` so a 120-seat block is one instanced entity, light the space so it reads at eye height (stating the lighting intent with `tune_look {intent}`; the exposure follows the measured picture, see CONTRACTS.md), and give every zone its own character. For a `minimal` brief it says to stay sparse.
5. **Richness review.** In the existing review loop, each round also shows the brief, the renders (eye height and overview and, for a building, the street-level exterior and a three-quarter aerial), an advisory block with histograms of the images (mean luminance, washed and crushed shares) and piece counts per brief element (matched by the model's `find` words in names, ids, tags and generator ids), the entity count and distinct kinds. The model compares the result with its brief (`inspect {groups:true}` reads repeated groups), lists what is missing or sparse, and what is over-filled (pieces overlapping or stacked at several heights, crowded walls, circulation blocked: the evidence marks an element well over its count as OVER), and any stand-in of the wrong kind, and fixes it with small patches. The judges decide; the loop ends when the model approves with nothing large open, on a stall, or at the round budget the host set for the quality loop (no separate ceiling). When the model approves while elements are still under half their count, it is sent back once per distinct set of shortfalls, naming them and the one-call layout the brief gave each (`how`: tier, grid, perimeter, wall, along, row, scatter, single), to build the rest or to say plainly why each stays short; progress changes the set, so a model that keeps building is asked again, and one that gives a reason is not. That ask does not count towards the stall detector.

## Run record

The `brief` event is kept in the chat record: the validated brief, the elaboration statement and reason, the reference decision (`generated | skipped | unavailable | failed`) with reason, prompt and provenance, and the user's edits. The studio view is bounded and revalidated when a chat is loaded.

## Offline planner

Unchanged. Offline there is no brief, no reference image and no review; the run is labelled as the offline planner as before.

## Limits

The brief is only as good as the model's knowledge of the kind of place. Counts are estimates for a size, not a quota; a hand-placed piece named unlike its element will read as missing in the evidence, which is why the model, not the count, judges.
